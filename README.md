# oncalendar

`oncalendar` is a Rust library for systemd calendar event expressions, the values you write in `OnCalendar=` in a timer unit. It parses an expression, prints the normalized form that `systemd-analyze calendar` prints, and lists the instants when the expression elapses after a given time, in a given time zone, with systemd's daylight saving time behavior. The expected results come from running the real `systemd-analyze calendar` in a pinned container.

## Status

v0.1 is implemented, and its normalization and elapses match `systemd-analyze calendar` on every fixture. The crate is not published on crates.io.

The repository holds:

- The library, in `src/`.
- The design, in [docs/architecture.md](docs/architecture.md).
- The oracle under `oracle/`, which runs the real systemd.
- The fixtures in `tests/fixtures/`, generated by the oracle.
- The lint, license, and weight gates.

## Usage

```rust
use oncalendar::CalendarEvent;

let event: CalendarEvent = "Mon *-*-* 09:00".parse()?;
assert_eq!(event.to_string(), "Mon *-*-* 09:00:00");

let local = jiff::tz::TimeZone::get("Asia/Seoul")?;
let after: jiff::Timestamp = "2026-01-01T00:00:00Z".parse()?;
let next: Vec<jiff::Timestamp> = event.upcoming(after, &local)?.take(2).collect();
// systemd gives 2026-01-05T00:00:00Z and 2026-01-12T00:00:00Z for this case.

assert!("*-*-* 25:00".parse::<CalendarEvent>().is_err());
```

`upcoming` can yield millions of instants per second for expressions such as `*:*:0/0.000001`, so always bound it with `take`. The library never reads `TZ` or `/etc/localtime`. To match systemd, pass `&jiff::tz::TimeZone::system()` as the local zone.

`upcoming` looks up a zone named in the expression, such as `daily Asia/Seoul`, in jiff's global database, which on Unix is the system copy. `upcoming_with(after, &local, &database)` takes the database as an argument. Use it in a container without tzdata, or to get the same answers on every host: turn on jiff's `tzdb-bundle-always` feature and pass `&jiff::tz::TimeZoneDatabase::bundled()`. Without that feature the bundled database is empty. In both functions a name must match the database exactly, letter case included.

## Features and weight

| Feature | Default | Adds |
| --- | --- | --- |
| `jiff` | on, through `system-tzdb` | `CalendarEvent::upcoming` and `CalendarEvent::upcoming_with`. Depends on `jiff` 1 with only its `alloc` feature. Works without `std`. |
| `system-tzdb` | on | Named time zones from the system time zone database. Turns on `jiff` and jiff's `std`, `tzdb-zoneinfo`, and `tzdb-bundle-platform` features. Needs `std`. |

With `default-features = false`, the crate parses and normalizes, and it depends on no other crate. Prototype measurements, stripped release executables:

| Build | Size | Cold release build |
| --- | --- | --- |
| No dependencies | 343,360 bytes | 0.3 s |
| jiff, `std` and `tzdb-zoneinfo` only | 569,616 bytes | 2 to 4 s on a loaded machine |

These numbers come from small prototypes, not from this crate. See [docs/architecture.md](docs/architecture.md) for the method.

MSRV is Rust 1.85, edition 2024.

The crate is `#![no_std]` and needs `alloc`, so it runs on embedded targets that have a global allocator. With `default-features = false`, and also with only the `jiff` feature, it builds for targets without `std`, such as `thumbv7em-none-eabihf`.

On such a target, pass a fixed offset or UTC as the local zone:

```toml
oncalendar = { version = "0.1", default-features = false, features = ["jiff"] }
```

Without `system-tzdb`, `upcoming` has no time zone database, so an expression that names a zone other than `UTC` returns `UnknownTimeZone`. To support names there, turn on jiff's `tzdb-bundle-always` feature and pass `TimeZoneDatabase::bundled()` to `upcoming_with`.

Code size for `thumbv7em-none-eabihf`, a minimal program built with `opt-level = "z"`, LTO, and `panic = "abort"` (measured once, built but not run on a device):

| Build | `.text` |
| --- | --- |
| Parse and normalize, no dependencies | 31,378 bytes |
| `jiff` feature, fixed offset as the local zone | 39,635 bytes |
| `jiff` feature and jiff's bundled time zone database | 292,796 bytes |

## Known differences from systemd

- An unknown time zone name, such as `daily Nowhere/Bogus`, parses. `upcoming` then returns `UnknownTimeZone`. systemd rejects it at parse time.
- Local time zone abbreviations, such as `daily KST`, are not supported. systemd accepts them only when the process time zone uses that abbreviation, and then elapses only while the abbreviation is in effect. A name that is both, such as `EST` under `TZ=America/New_York`, is read by this library as the database zone.
- The local time zone is an argument. Parsing reads no file and no environment variable. `upcoming` with a named zone reads the time zone database through jiff, which honors `TZDIR`.
- Where systemd gives up computing an elapse ("Failed to determine next elapse"), the library still answers. One such input is `Sun *-03-08..14 02:30 America/New_York`, which never elapses. systemd also gives up on some expressions whose next elapse is months away and nowhere in a gap, such as `*-5/6-21,12 7,20..21:41,11/18:26` in `Europe/London` from 2026-12-09. From a later base time it answers, and the answer matches the library's.
- In `Pacific/Chatham`, where the clock jumps from 02:45 to 03:45, systemd leaves out some times that exist on that day and gives up on others, such as `*:45`. The library elapses at every time that exists.
- Named zones come from jiff's time zone database, which on Unix is the system copy. In a container without tzdata, named zones fail. To bundle the database, turn on jiff's `tzdb-bundle-always` feature in your own `Cargo.toml` and call `upcoming_with` with `TimeZoneDatabase::bundled()`. A name is accepted when the database has it. The bundled database has `EST`, `UCT`, `Zulu`, and `W-SU`, while a Debian system without the `tzdata-legacy` package has none of them, so systemd there rejects `*-*-* 10:00 EST` and the library with the bundled database accepts it.
- Near some daylight saving changes the two still differ (observed): in `America/Havana` after the midnight gap, `9/14,1:4/22` elapses in systemd at 01:26 and in the library at 01:04; in `Europe/Dublin`, a candidate in the spring gap makes systemd move on to a later day; in some folds in `Asia/Gaza` and `Africa/Cairo` systemd takes the second pass where the library takes the first. See [docs/architecture.md](docs/architecture.md#known-differences-from-systemd).
- Some fractional repetitions in seconds, such as `*:*:0/40.9`, never elapse at their start value in systemd (observed), while the library elapses there. `*:*:0/40.5` and whole-second steps agree.

## How it is verified

- `oracle/check.sh` reruns the real `systemd-analyze calendar` in Docker and fails if `tests/fixtures/expected.tsv` is stale.
- `tests/oracle.rs` checks parse results, normalized strings, and elapse times against `tests/fixtures/expected.tsv`, without Docker.
- `tests/normalize.rs` checks the normalized strings again without any feature, so the build without dependencies is covered.
- `tests/robustness.rs` checks that hostile input never panics, never loops, and never echoes into error messages.
- `scripts/check-security.sh` runs the no-`unsafe` and panic lints, `cargo deny`, and the robustness tests.
- `scripts/check-weight.sh` gates the dependency count and reports build time and size.
- `scripts/check-no-std.sh` builds the crate without default features for `thumbv7em-none-eabihf`.
- `scripts/check-features.sh` runs clippy on every feature combination, and `scripts/check-minimal-versions.sh` runs the tests with every dependency at its lowest allowed version.
- `scripts/check-package.sh` checks the files that would be published and builds the packaged crate.
- `scripts/check-workflows.sh` runs `actionlint` and `zizmor` on the CI configuration.
- `scripts/fuzz.sh` runs the `cargo-fuzz` targets in `fuzz/`: parsing any input and printing it back, and computing elapses for any accepted expression.
- CI runs the tests on Linux, macOS, and Windows, and the other checks on Linux. A weekly run checks for new advisories, rebuilds the oracle image, and fuzzes for longer.

## Contributing

The implementation is clean-room. Use only the `systemd.time(7)` manual and black-box runs of `systemd-analyze calendar`. Do not read the systemd source or other OnCalendar implementations. [docs/architecture.md](docs/architecture.md) explains why and how to add a fixture.
